\chapter{Understanding SVD Files and the PAC Generation Process}
\label{ch:chapter-02}
\chapthumb{2}

\begin{quote}
    \textit{``The SVD is the only document about this chip that cannot be out of date, because the
    vendor generates the same file the debugger uses.''}
\end{quote}

Before a single line of HAL can be written, something has to know what registers exist, where they
live, which bits mean what and what the reset values are. On ARM that something is an SVD file, and
the tool that turns it into Rust is \codeinline{svd2rust}.

This chapter is not a tutorial on running \codeinline{svd2rust}. It is about the two things that
actually matter: what the generated code looks like when you have to read it, and what the SVD knows
that no other document does — including the register that explained why a week of work had produced
zero results.

\begin{keytakeaways}
    \item An SVD is XML describing every peripheral, register, field, enumerated value and reset
          value. It is the same file the vendor's debugger uses.
    \item \codeinline{svd2rust} turns it into a PAC: a \codeinline{Periph<T, ADDR>} per peripheral, a
          register block, and type-safe readers and writers per field.
    \item The generated field descriptions are documentation you can trust more than the manual,
          because they travel with the register accessors you are already calling.
    \item A register the SVD names \emph{Block Enable} is not a suggestion. It was the missing write
          in an accelerator that had never executed.
    \item PAC-level examples are an antipattern for applications and indispensable as proof: they are
          the only place a HAL can be checked against the hardware.
\end{keytakeaways}
