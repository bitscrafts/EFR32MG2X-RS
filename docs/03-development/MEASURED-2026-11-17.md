# Measured on the board, 2026-11-17 — for the slides and the report

Every number below came off the XIAO MG24 Sense (`2886:0062:28DB6336`) through the mailbox or the cycle
counter. Nothing here is an estimate, and nothing here is a datasheet figure. Where a number is missing, it
says so instead of being filled in.

## Core clock

```
19 MHz          the reset default of the HFRCO. Three independent sources agree:
                emlib SystemSYSCLKGet() = 19 000 kHz; CMU_ClockFreqGet(CORE) = 19 000 kHz;
                DWT against LFRCO = 18,98 MHz (32 800 LFRCO ticks over 19 000 025 cycles)
78 MHz          the part's maximum (Seeed: "ARM Cortex-M33 @ 78MHz"), reached only by programming the
                DPLL. Nothing in this repository does that yet: the HAL has HFXO but no DPLL.
source          AN0004.2 §2.3.3: "The HFRCO defaults to operation in the 19 MHz band but can be switched
                to operate in one of the other preset frequency bands by changing the FREQRANGE bit field"
```

## Microphone

```
sustained rate  303 148 samples/s, 62,7 core cycles per sample (polled SINGLE conversions)
                two runs, 303 148 and 303 149 samples in 19 000 068 / 19 000 056 cycles -> 1 sample apart
windows         2 376 windows/s of 128 samples = 304 141 samples/s (the two phases agree)
root cause      2026-11-17: the HAL and BSP never wrote GPIO_CDBUSALLOC.CDODD0, so PC9 (an odd pin) never
                reached ADC0 and the converter returned a flat zero, which level() reported as rms=2048.
                After the fix: 20 distinct values in 128 samples, band 2610..2638 (bias plus noise).
```

## What one audio window costs the CPU

```
decimation factor  19 (303 148 / 16 000 = 18,95)
acquire+decimate   184 048 cycles for 4 864 raw samples = 37,8 cycles per sample
8 Goertzel bands   46 044 cycles over the 256-sample window = 22,5 cycles per step
total per window   230 092 cycles = 12,1 ms of CPU for 16 ms of audio = 76 % of the core
```

And the same acquisition at the rates that matter — this is the number that decides the design:

```
303 148 Hz     11,47 M cycles/s = 60,4 % of the core just to ask for samples
 16 000 Hz      0,61 M cycles/s =  3,2 %
  8 000 Hz      0,30 M cycles/s =  1,6 %

at 16 kHz: acquire 0,61 M + bands 2,88 M = 3,48 M cycles/s = 18,3 % of the core, leaving 82 %
```

Conclusion for the report: **oversampling at 303 kHz and decimating is the wrong path** — the cost is in
asking, not in the arithmetic. Sample at the rate you use, paced by a timer, and let the CPU pop the FIFO.

## MVP (matrix/vector processor)

```
driver          crates/efr32mg2x-hal/src/mvp/mod.rs — Mvp::take, add_fp16, typed errors
measured        N=64 fp16 element-wise add, self-check PASS (every result 2.0):
                  MVP   289 cycles (12 configuration writes + 64 hardware adds)
                  CPU   921 cycles (64 adds in a loop)
                  ratio 3,18x in favour of the MVP
caveat          the CPU loop adds the words as integers; the MVP adds real binary16. The CPU figure is
                therefore a lower bound, generous to the CPU.
not measured    MAC with accumulation (needs encodings from sl_mvp.h that the repository does not have)
```

## RAM and BLE — the answer to "1 184 KB does not fit"

```
1 s at 303 kSa/s, f32      1 184 KB   -> 4,7x the 252 KB available
1 s at  16 kHz, i16           31 KB   -> the RAM holds 8 s
dosimeter result           24 B/s     -> Leq(4) + dose(4) + 8 bands(16)
BLE practical throughput   ~127 KB/s  (4 x 244 B per 7,5 ms interval, MTU 247)
raw 303 kSa/s needs        592 KB/s   -> 4,7x more than the link carries
```

So: the dose is computed on the device and the phone receives 24 B/s. Raw audio to the phone is possible at
16 kHz (31 KB/s, a quarter of the link) but it is a diagnostic mode, not the product.
