# Session 2026-11-14 — the radio works, and a phone can use it

Session record, in the order things were found. The state lives in `HANDOFF.md` and `docs/04-reference/BLE-STATUS.md`;
this is the account of how it got there, because the reasoning is usually more useful than the conclusion.

## What was asked

The request that governed the session was blunt: *the solution does not appear, days pass*. So the measure of success was
not "the stack links" but "a phone shows the sensor", with everything needed to reproduce it.

## What closed

1. **A GATT server a client can actually use.** A client connects, reads a characteristic, writes to another,
   subscribes, and the firmware echoes the written bytes back in its notifications. The echo is the evidence: a read-back
   can be answered from the host's cache, so it proves nothing; bytes that come back from inside the radio had to cross
   the link.
2. **The BME680 as a standard Environmental Sensing service** (`0x181A` with `0x2A6E`, `0x2A6F`, `0x2A6D`). This needed
   16-bit UUID support in the GATT database builder — the API only exposed 128-bit UUIDs, and a 128-bit UUID means a
   phone shows hex instead of a labelled, decoded value. Verified on the owner's phone with nRF Connect and byte for byte
   by `scripts/host-env-verify.py` (`dd0c` → 32.93 °C, `7e18` → 62.70 %, `888a0100` → 101.00 hPa).
3. **The example matrix**: thirteen examples build, flash, run, and the eight whose job is to transmit are seen on the air
   by a separate host. `scripts/ble-matrix-all.sh` produces the table in one command.
4. **The arena survives a connection.** Before: `hl=72` with a client attached, i.e. 72 bytes of 64 KiB reachable.
   After: 53720. The cause was a vendor path writing about 136 bytes into a 64-byte allocation, so the write reached the
   following block's header and made everything after it unreachable.

## Four defects that were mine, not the vendor's

- **`start_advertising` is not connectable.** It sends a non-connectable PDU: the phone sees the name, tries to connect,
  and the attempt never completes — no error on either side. Anything a client must use needs `start_connectable`.
- **A connectable advertiser stops when a central connects** and must be restarted on `Disconnected`. Without that the
  product works for the first phone and never again. The board looked "not advertising" for an hour because of this.
- **`at += push(..)` where `push` returns the advanced offset** doubled the offset and panicked with `slice_index_fail`.
  It was found by halting the core and resolving the program counter (`scripts/where.sh`), not by re-reading the source.
- **`audit()` counted free blocks as damaged.** Free blocks carried no canary, so a heap that had never served a
  connection reported "1 of 15 damaged" — an instrument lying in the direction of "there is a bug", which is just as
  costly as one lying in the other direction.

## Instruments that had to be fixed before the measurement meant anything

- **A mailbox record survives a reset.** After flashing a new example the record still belonged to the previous image,
  with bytes a client had written minutes earlier, and the matrix credited the wrong image with the wrong evidence.
  `scripts/clear-mailbox.sh` now runs before every flash.
- **`read-mailbox.sh` cut the record at 64 bytes**, removing exactly the fields that explain a failure (`ld=`, `ad=`,
  `hl=`). It reads 200 bytes now.
- **A Bluetooth device learned in one scan is temporary**: connecting from a *new* process answers "not available" for a
  board that is transmitting perfectly. The client has to keep discovery alive or do everything in one session —
  `scripts/host-env-verify.py` does the latter.
- **The host's `bluetoothd` can stop reporting entirely** while the radio is fine. `scripts/host-rawscan.sh` uses the raw
  HCI path to tell those two cases apart; Wi-Fi on the same USB dongle is checked after every controller operation,
  because it is the only route out of the machine.

## What is not done

- **Pairing.** With the security manager enabled the request is accepted and then fails at a DHKey check with
  `pg=0 pe=0 pa=0` — none of the PSA entry points were called — so the fault is before key generation. The PSA layer
  (P-256, AES-CMAC, AES-CTR, AES-ECB) is written and verified on the board by a startup self-test (`ec1 pk65 dh1`).
- **Gas resistance.** The driver reads temperature, pressure, humidity and the variant byte. The heater, `res_heat` and
  the `par_g*` curves are not implemented, so the reading that distinguishes a 680 from a 688 is missing.
- **The advertising rate.** Unmeasurable here: the adapter captures about 8% of the air, so counts cannot become a rate
  without a controllable receiver.
- **CI for the vendor-dependent crates.** The Silabs sources are excluded from git under MSLA, so a clean clone builds
  the PAC, HAL and libraries but not the radio or the BSPs.
