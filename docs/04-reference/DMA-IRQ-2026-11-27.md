# LDMA done interrupt: the core sleeps, and `IEN` is the gate (2026-11-27)

Item C2-DMA.4 of the HAL night queue. Question: does a memory-to-memory LDMA transfer end by **interrupt**, with the
core asleep instead of polling, and is the controller's `IEN` the bit that delivers it?

Answer, measured on the XIAO MG24 Sense: yes, and the control shows it is `IEN` and not the completion itself.

## The record

Three flashes, three boots, byte-identical mailbox records, `status=PASS` in all three:

```text
dmairq: ok=1 n=2047 am=2047 irq=1 sp=1 tk=0 g=1 ad=1 af=0 cm=2047 cirq=0 csp=6 ctk=6 cg=0 cd=0 cf=1
```

| field | meaning | value |
|---|---|---|
| `n` | words per transfer | 2047 |
| `am` | words that arrived, gate open | 2047 |
| `irq` | `LDMA_IRQHandler` entries, gate open | 1 |
| `sp` | times the wait entered `WFI`, gate open | 1 |
| `tk` | `SysTick` ticks spent in the wait, gate open | 0 |
| `g` | `IEN.CHDONE[0]` read back at the end of the gate-open run | 1 |
| `ad` / `af` | wait returned done / `DONE` flag still set at return | 1 / 0 |
| `cm` | words that arrived, gate closed (control) | 2047 |
| `cirq` | handler entries during the control | 0 |
| `csp` | `WFI` entries in the control | 6 |
| `ctk` | ticks spent in the control | 6 |
| `cg` | `IEN.CHDONE[0]` in the control | 0 |
| `cd` / `cf` | control wait returned done / `DONE` flag set at return | 0 / 1 |

Harness: `crates/efr32mg2x-hal/examples/hal_dma_irq.rs`. Driver: `crates/efr32mg2x-hal/src/dma/irq.rs`
(`Gate`, `Pending`, `Wait`, `service`, `wait`, `start_interrupt`).

## What the two runs say

Both runs program the same descriptor (`DONEIEN` bit 20 set), leave the `LDMA_IRQ` vector unmasked in the `NVIC`,
move the same 2047 words from the same source into two different destinations, and differ in exactly one bit:
`IEN.CHDONE[0]`.

**Gate open (`Gate::Enabled`).** The core arms, enters `WFI` once (`sp=1`), and the LDMA vector brings it back
(`irq=1`). The deadline clock has not advanced (`tk=0`), so the wake was not `SysTick` and no other source was
pending: the interrupt that ended the sleep was the controller's. The handler cleared the flag (`af=0`), and the
data is complete (`am=2047`). One `WFI` also says the wait body never spun -- a polling loop would have run thousands
of iterations and the counter would show them.

**Gate closed (`Gate::Closed`, the control).** The transfer still runs to completion (`cm=2047`) and the `DONE` flag
still latches (`cf=1`), but no handler entry happens (`cirq=0`). The wait could not be satisfied by the flag it can
read, because it does not read it as a completion criterion -- it waits for the handler's record -- so the deadline
is what ended it (`cd=0`, `ctk=6 > 5`). Six ticks is also the proof that `WFI` really sleeps: the only thing that
woke the core in this run was `SysTick`.

The pair is the point. "The transfer completed with an interrupt" would be worth nothing without the near miss where
the same transfer completes, the flag is set, and the core is never told.

## Facts measured here

1. `IEN.CHDONE[channel]` is the delivery gate for a completed descriptor. `IF` latches whether or not the bit is set
   (`cf=1` with `cg=0`): the flag is the hardware's record, the enable bit is the decision to act on it.
2. `IF` for LDMA is cleared through the `+0x2000` alias window, not by writing 1 to the plain register -- the same
   window `LETIMER0`, `I2C` and `GPIO` measured. `service()` clears every bit it read, because the vector line is a
   level: a handler that leaves one bit set re-enters for ever.
3. `WFI` is a real sleep here: with nothing pending the core stops, and the control shows six wake-ups, each one a
   `SysTick` the wait counted. A busy loop would have produced one `WFI` entry at most and a much larger tick count
   for the same wall time.

## What is **not** measured, and stays out of the claim

- **EM2.** The wait uses `WFI` in EM0, not `Sleep::enter` (EM2). "The core sleeps" means the core is not executing,
  not that the part is in a low-energy mode. Turning EM2 on for this path is a separate item.
- **Callbacks.** There is no per-transfer callback: the handler sets a bit per channel, the wait polls that bit once
  per wake. A callback per descriptor is application policy and is not in this driver.
- **Peripheral-triggered async.** The armed transfer is memory-to-memory with a software request. A peripheral request
  routed through the crossbar with the interrupt ending the wait is not measured.
- **Channels 1-7.** The typed start path programs channel 0 only, the same restriction the blocking API has.
- **Error interrupts.** `IEN.ERROR` (bit 31) is left as the caller set it; nothing here measures it.
