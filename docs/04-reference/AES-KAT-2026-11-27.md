# RADIOAES: the AES engine driven by scatter-gather descriptors, against two published known answers

Date: 2026-11-27. Item 8 of `_tmp/night/STATE-NIGHT2.md` (queue: "radioaes / KAT"). Board: XIAO MG24 Sense
(EFR32MG24B220F1536IM48-B) on the bench at `lnx`, CMSIS-DAP probe. Example:
`crates/efr32mg2x-hal/examples/hal_aes_kat.rs`; driver: `crates/efr32mg2x-hal/src/aes/mod.rs`; words and vectors:
`src/cores/aes.rs` (+ `libraries/aes-core`, seven host tests and a printed table); hand-out: `Board::aes`.

Nothing is transmitted. `RADIOAES` lives in chapter 5 of the reference manual and shares the radio's address
neighbourhood, but it is its own block in the **EM1** power domain behind `CMU_CLKEN0.RADIOAES`; `CMU_RADIOCLKCTRL` is
never written and the transceiver is never enabled. The measurement below is a cipher, not a transmission.

## The interface, in one paragraph

The block has no key, data or mode register. A fetcher and a pusher walk descriptor lists in RAM -- four words each,
`{address, next, length, tag}` -- and the crypto core's parameter space is filled by *configuration blocks* in the fetcher
chain, whose tag carries the parameter offset: key at 8, mode word at 0. That interface is the one the vendor's BLE driver
uses (`sli_protocol_crypto_radioaes.c`, vendored in `crates/efr32mg24-bluetooth-sys/vendor/support`); no code was copied
from it, and the tag arithmetic it defines is re-exported from `cores::aes` so the words can be read and tested on the
host (`cargo run -p efr32mg2x-aes-core --example vectors`).

## The record

Three flashes of the formatted tree, three boots, `status=PASS` in all three, byte-identical:

```
aes: ok=1 n=4 ct=69c4e0d86a7b0430d8cdb78070b4c55a c2=3ad77bb40d7a3660a89ecaf32466ef97
     pt=00112233445566778899aabbccddeeff f0=0x00000000 f1=0x00000012 st=0x00000000 hw=0x05030127
```

| field | meaning |
| --- | --- |
| `ok` | every check below held |
| `n` | blocks put through the engine: FIPS encrypt, the same repeat, the second vector, the decrypt |
| `ct` | the ciphertext read back for FIPS-197 C.1: key `000102...0f`, plaintext `001122...ff` |
| `c2` | the ciphertext read back for NIST SP 800-38A F.1.1 block 1: key `2b7e1516...4f3c`, plaintext `6bc1bee2...172a` |
| `pt` | the plaintext the decrypt of `69c4e0d8...c55a` returned under the FIPS key |
| `f0` | `IF` after clearing and before the first start -- the control that the flags were empty |
| `f1` | `IF` when the last operation returned: `0x12` |
| `st` | `STATUS` at the end: both busy bits clear, FIFO empty |
| `hw` | `BA411E_HW_CFG_1`, read from the block: `0x05030127` |

The two ciphertexts are the published values, byte for byte, with the vectors written into the source in the order the
standards print them. The bytes go to the engine as they are -- no per-word reversal -- and come back in the same order;
that is a measured property of this core, not an assumption (the descriptor carries a byte buffer and the core reads it as
big-endian words, which is why the standards' order survives).

## What each run rules out

1. **A descriptor chain that is written and never fetched.** `ct` equals the published ciphertext and every output buffer
   starts as `0xA5`: a run that never moved a byte fails on the first comparison, and one that wrote a stale value fails
   on the bytes.
2. **An answer that is right for the wrong reason.** `c2` is a *different key and a different plaintext*. A key the engine
   ignores would still pass a single vector if that vector happened to match what the engine does with anything; it
   cannot pass two.
3. **A repeat that is not stable.** The FIPS call is made twice and the two blocks must be equal -- the record's `ct` is
   the first one, and a mismatch fails `ok`.
4. **A mode word that is fetched but not applied.** `pt` is the decrypt of `ct`'s published value under the same key, in
   the same driver, through the same chain with one bit changed in the mode word. An engine that always encrypts returns
   the ciphertext again and fails here.
5. **Control: the flags were empty before the first start.** `f0 = 0` after `IF_CLR`, so `f1` is a flag this run set.
6. **Control: the near miss, on the board.** A separate image (`hal_aes_control`, removed after the run) ran the same
   call with the FIPS key's first bit flipped:
   `aesc: ok=1 ran=1 w=1 d=16 ct=9bc9ea753251875a97f3a6cab33f112b` -- the engine wrote a block, all sixteen bytes moved,
   and it is not the published answer. That is what makes `ct` a measurement rather than a comparison that always passes.
   The wrong-key ciphertext was then recomputed on the host with
   `openssl enc -aes-128-ecb -K 010102030405060708090a0b0c0d0e0f -nopad` and came back `9bc9ea75...112b`: the board
   agrees with an independent implementation, on a key the standards do not publish.

## Three facts paid for, and one that is documentation rather than measurement

1. **`STATUS.SOFTRSTBSY` is not a completion handshake, and waiting on it is a boot that reports nothing.** The first
   image of this item wrote `CTRL.SWRESET` and waited for the bit to clear. It never did, and the record was
   `aes: RADIOAES refused its reset`. The probe image that followed, `aesp: st0=0x00000040 c0=0x00000010 st1=0x00000040
   st2=0x00000040 p=200000 c1=0x00000010 st3=0x00000040 c2=0x00000000 hw=0x05030127`, says why: the block comes out of
   reset with `SOFTRSTBSY` already set (bit 6) and `CTRL.SWRESET` already set (bit 4), writing `SWRESET` again changes
   neither word, and clearing `CTRL` to zero leaves the status bit set as well -- 200 000 polls later it is still set.
   The vendor driver never writes `SWRESET` at all: its first write is `CTRL = FETCHERSCATTERGATHER |
   PUSHERSCATTERGATHER`, which is what `Aes::run` does. The driver therefore has **no** reset step and checks instead
   that the core identifies itself.
2. **`IF` after a completed chain is `0x12`, not the end-of-block bits.** The fetcher and pusher report *stopped*
   (bits 1 and 4) rather than *end of block* (bits 0 and 3) when the last descriptor's `next` is the stop marker. The
   record carries the raw word; nothing in the driver waits on either flag, because the busy bits in `STATUS` are what
   say the operation finished.
3. **This part's core publishes `0x05030127`, not the header's reset word.** `efr32mg24_aes.h` gives
   `_AES_BA411E_HW_CFG_1_RESETVALUE = 0x05010127`; the block on this board reads `0x05030127` -- the same shape, with the
   generic-config nibble different. Nothing in this crate writes that register; the word is the core's own description of
   itself and the driver only reads it (`Aes::core_config`, and the `NotPresent` refusal for an all-zero or all-ones
   read). No capability is claimed from it beyond "the core answered".
4. **The bus gate is `CMU_CLKEN0.RADIOAES`, bit 2** -- from the `CMU_CLKEN0` table of the reference manual, not from a
   fault: `Board::aes` sets it before the first read, so this run has no image that omits it, and this file does not
   claim a `BFAR` it did not see. What the run does show is that the gate in `CLKEN0` is sufficient: with it set and
   `RADIOCLKCTRL` untouched, the core answers and computes.

## What this does not claim

No mode other than ECB, no key other than 128 bits, no chaining, no throughput, no interrupt path (`IEN` is left clear),
no DMA to or from the crypto core outside the descriptor chain it walks itself, and no use of the block from EM2. The
buffer path is one block per call: `AES_OFFSET_IV` and the 256-bit key offset are defined in `cores::aes` for the next
mode but are exercised by nothing here.
