# What is missing for `ble_gatt`, measured

The example does not link, and the reason is specific: **twelve undefined symbols**, in three groups
that need three different answers. Two of the three are ours to solve now; the third is a licence
question.

Measured with:

```bash
cargo build --release --target thumbv8m.main-none-eabihf -p efr32mg24-radio \
  --features gatt --example ble_gatt 2>&1 | grep -oE "undefined symbol: [A-Za-z0-9_]+" | sort -u
```

## Group 1 — the heap (ours, ~40 lines)

```text
sl_malloc
sl_free
```

The host stack allocates. In a vendor project these come from `sl_malloc.c`, which wraps a static
heap; nothing about them is proprietary. A `static mut [u8; N]` plus a free list, or a bump allocator
if the stack never frees — measurable, because a stack that frees needs a real allocator and one that
does not can use a bump pointer and prove it by watching the high-water mark.

**Status: not implemented.** It is the cheapest of the twelve and it unblocks nothing on its own.

## Group 2 — PSA crypto (needs vendor libraries, 10 symbols)

```text
psa_crypto_init            psa_destroy_key     psa_import_key        psa_mac_abort
psa_mac_sign_finish        psa_mac_sign_setup  psa_mac_update        psa_reset_key_attributes
psa_set_key_domain_parameters                  sli_psa_context_get_size
```

The connectable path pulls the bonding/encryption code, which calls PSA. Silicon Labs ship this as
`libpsa_crypto.a` and `libmbedtls.a` — separate artefacts with their own licence terms, **not present
in this repository and not present in the archived copy of this project**.

Three ways forward, in order of honesty:

1. **Vendor the two libraries** for xg24 from the same SDK version as the Bluetooth blobs. Nothing else
   is needed; the symbols then resolve. This is the correct path.
2. **Write stubs that return `PSA_ERROR_NOT_SUPPORTED`**, build with `--features gatt-nosec`, and test
   whether a *non-bonding* connection works. The risk is real and must be written down: the stack may
   treat a failed `psa_crypto_init` as fatal, and if it does not, the device silently has no security.
   Only acceptable if the build says so in its name and its documentation.
3. **Give up on connectable.** Advertising carries a verdict; a connection carries a conversation. For
   a sensor, the first is often enough — which is why this project's IMU and fall examples are
   broadcast, and why they work today.

## Group 3 — the GATT database (ours, and the example was wrong about it)

This one is not a link error, and it would have been the next failure. `ble_gatt` used
`CharHandle(0x000B)` — a handle that exists only if a GATT database *generated by the SDK's GATT
Configurator* is compiled in. This project has no such file, so the stack has no services at all and
the handle is meaningless.

Two ways to get a database:

- **Generated** (`gatt_db.c` from the Configurator). Requires Simplicity Studio and a chosen service
  set. Not reproducible from this repository.
- **Dynamic**, at runtime. The host blob exposes the whole builder API, verified present in the
  bindings:

  ```text
  sl_bt_gattdb_new_session     sl_bt_gattdb_add_service     sl_bt_gattdb_add_uuid
  sl_bt_gattdb_add_included_service                         sl_bt_gattdb_start_service
  sl_bt_gattdb_start_characteristic                         sl_bt_gattdb_commit
  sl_bt_gattdb_remove_*        sl_bt_gattdb_stop_*          sl_bt_gattdb_abort
  ```

So a service can be built from Rust, with no Configurator and no generated C. **That is the path this
project should take**, and it is a self-contained piece of work in `efr32mg24-radio`: build the service,
start it, and read back the handles the stack assigns — which is also the answer to "where does
`CharHandle(0x000B)` come from?" (nowhere; it must be read back, not assumed).

## The order to do this in

1. **GATT database builder** in `efr32mg24-radio` — no vendor dependency, testable by inspection, and it
   removes the wrong-handle assumption from the example.
2. **`sl_malloc` / `sl_free`** — a documented static heap with a high-water mark in the mailbox.
3. **PSA**: vendor the two libraries, or decide deliberately to ship a `gatt-nosec` build and say so.

Until step 3, `ble_gatt` stays out of the gate's example count. The `--features gatt` build failing with
this list is the honest state, and it is reproducible: one command, twelve names.

## What does not need any of this

`ble_beacon`, `ble_advertise_custom`, `ble_scanner`, `module_ble_beacon`, `module_ble_motion`,
`module_ble_fall`, `base_ble_env` — all link today, and all of them carry a payload a phone or a second
board can read. The gap is *bidirectional* Bluetooth, not Bluetooth.
