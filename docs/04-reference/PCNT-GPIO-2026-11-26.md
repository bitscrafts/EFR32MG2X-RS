# PCNT0 counting a GPIO PRS producer — 2026-11-26

`PCNT0` was the only family in `COVERAGE-BOUNDARY-2026-11-25.md` with a producer already proven on the board and
nothing written to count it. This record is the first measurement of the block: what it counts, what it refuses, and
where its ceiling is.

- **Probe:** `crates/efr32mg2x-hal/examples/hal_pcnt_gpio.rs`
- **Driver:** `crates/efr32mg2x-hal/src/pcnt.rs`, handed out by `Board::pcnt()`
- **Board:** XIAO MG24 Sense, `EFR32MG24B220F1536IM48-B`, flashed over SWD from `lnx`
- **Producer:** the pad under test, moved by its own pull resistor, then as a push-pull output (item 6 of the night
  queue proved the pull-moved pad gives four rising edges per eight writes)

## The record, from two runs

Both runs printed the same fields, `status=PASS`:

```text
pcnt: ch=3 cfg=0x00000100 ctrl=0x00000010 st=0x00000000 a=4 lv=4 b=2 c=3 off=0 stop=0 q=0 mm=0 p0=4 ok=25000 bad=50000 g=77 e=200 of=0 ar=4 br=2 cf=2 cm=4 hr=4 em=8 if=0x00000000
```

| field | meaning | value |
|---|---|---|
| `a` | 8 pull toggles, rising edges counted | 4, equal to the 4 rising edges the pad made (`ar=4`) |
| `lv` | the same count read with the counter still running | 4 — the read is live |
| `b` | 5 toggles, rising | 2 |
| `c` | the same 5 toggles, falling | 3 |
| `off` | channel `Off`, pad still moving | 0 |
| `stop` | counter stopped, producer connected, pad moving | 0 |
| `q` | channel on, counter started, pad left alone | 0 |
| `mm` | producer moved to channel 0, consumer left on 3 | 0 |
| `p0` | consumer moved to channel 0, pad PA0 toggling | 4 |
| `ok` | highest ladder rate counted in full | 25 kHz |
| `bad` | first ladder rate not counted in full | 50 kHz |
| `g` / `e` | count at that rung against 200 pulses | 77 / 200 |
| `of` | highest ladder rate, channel `Off` | 0 |
| `cm` / `cf` | pad moves and falling edges the software saw in `c` | 4 / 2 |

`em=8` is the stopped-counter phase: the pad moved on all eight writes while the counter stayed at zero.

## Facts the measurement produced

- **The PRS path counts.** The same edge that makes the IADC convert makes `PCNT0` increment, with no CPU work per
  event. `CFG.S0PRSEN` plus `PRS.CONSUMER_PCNT0_S0IN.PRSSEL` is the whole route; without the consumer word the counter
  listens on channel 0 and the control phase `mm` reads zero.
- **`CFG` is refused while `EN` is set.** The write raises a precise bus error: `CFSR = 0x00008200`
  (`PRECISERR | BFARVALID`), `HFSR = 0x40000000`, `BFAR = 0x5903_000C` — `PCNT0 + 0x0C`. The core halts. Every
  configuration write in the driver therefore happens with `EN` low.
- **Clearing `EN` is not instantaneous, and the first read of the handshake lies.** `EN` cleared, the next read
  returned `0x2` (`DISABLING` set) and a `CFG` write immediately after it faulted again. The wait has to start before
  the flag is raised: the driver waits ~200 µs and only then polls `EN.DISABLING`.
- **`CMD` is synchronised** (`SYNCBUSY.CMD` exists). Two commands inside one synchroniser period fault at
  `BFAR = 0x5903_0014`. Every command write is gated on `SYNCBUSY`.
- **`TOP` resets to `0x00FF`, not `0xFFFF`.** A counter left at reset wraps after 255 events; on a 200-pulse rung that
  would read back as the remainder. The example sets `0xFFFF` before any count is believed.
- **There is no capture command.** The queue entry for this item said `CNT` is read "through `CMD.CAPTURE`"; `CMD` on
  this part has reset, load, start and stop bits only and `CNT` has no writer. A read with the counter running returned
  the same value as the read after `CMD.STOPCNT` (`a=4 lv=4`), so the plain read is live.
- **`CFG.MODE = EXTCLKSINGLE` with `CLKSEL = 1` counts the branch, not S0IN.** Measured while the documented mode was
  still `EXTCLKSINGLE`: 88 counts in a 2.6 ms window and 139 in a 4 ms window, both ≈ 33 kHz, identical whatever the pad
  did. The external-clock mode wants the dedicated `PCNT_S0` pin as the block's clock.
- **`CLKSEL = 2` with a routed GPIO leaves the block without a clock.** `GPIO.PCNT0_S0INROUTE` was written for PC3 and
  `CMU.PCNT0CLKCTRL.CLKSEL` set to the external pin; with the pad static, `EN.DISABLING` stayed set indefinitely and the
  next `CFG` write faulted (`BFAR = 0x5903_000C`, `EN = 0x2` on read-back). The routed GPIO is not the `PCNT_S0` clock,
  and that path is not offered by the driver.
- **The sampled mode's ceiling sits between 25 and 50 kHz.** 200 pulses at 20 µs spacing (25 kHz nominal) were counted
  200 of 200; the same 200 at 10 µs (50 kHz nominal) gave 77. `delay_us` has its own call overhead, so the real spacing
  is longer than nominal and the 25 kHz rung is a conservative claim. The branch behind the sampling runs at 32.768 kHz
  (LFRCO), which is the right order for the wall.
- **A phase boundary can add one count.** In `c` the counter read 3 falling edges while the software saw 2 after the
  counter started (`c=3 cf=2`). Phases that start with the pad at the polarity's resting level count every edge exactly
  (`a`, `p0`); the boundary case is bounded in the example rather than explained, and explaining it is open.

## Fixes made elsewhere, and their state

Two defects were found while this measurement was being built, both from faults on the way to it:

- `Board::pace_microphone` faulted on its **second** call (`BFAR = 0x4004_8004`, `TIMER0 + CFG`). It cleared `EN` and
  wrote `CFG` in the next instruction; a block that was already running had not stopped. The fix waits for
  `EN.DISABLING` with an initial margin, and `pwm::Timer0::take` got the same wait.
- Both fixes are in the tree, and **neither is re-measured here**: the final example does not call `pace_microphone`,
  and no example drives `pwm::Timer0::take` twice. Re-running `hal_adc_prs_timer` (which paces once) and a double-pacing
  probe is the next step for them.

## What is not proven

- The exact ceiling: 25 kHz followed, 50 kHz not, nothing measured between them.
- Any producer faster than the pad: the ladder is limited by `delay_us`, and the timer route to a pad was not usable as
  an instrument here (a poller sampling `DIN` once per millisecond read zero changes for the timer's square wave and for
  the CPU-driven output that the counter demonstrably counted, so the poller was the broken part, not the route).
- The pad-clocked path (`CLKSEL = 2`) and therefore any claim about counting above the sampling ceiling.
