# EUSART1, and the loopback that closes through the pad — 2026-11-27

`EUSART1` was the last row of the coverage boundary that read "compiled, not measured". As with `TIMER1`–`TIMER4`, the
reason was in the source and not on the bench: `eusart` held one concrete `Eusart0`, so the second block had no driver
to measure.

## What was done

- `eusart/mod.rs`: the driver is generated by `impl_eusart!(Name, Regs)`, instantiated for `Eusart0` and `Eusart1` —
  two concrete types, one body, the same shape `timer` took today.
- `Board::eusart1_async()` — one claim (`Slot::Eusart1`, `SLOT_COUNT` 22), the `CLKEN1.EUSART1` gate, and nothing else:
  **this part has no `CMU_EUSART1CLKCTRL`**, so `EUSART1` is clocked from `EM01GRPCCLK` with no per-peripheral selector.
  That asymmetry is why the two blocks looked more different than they are.
- `Board::route_eusart1_async()` — and this turned out to be required, not optional.
- `examples/hal_eusart1_loopback.rs` — the instrument.

## The finding: `CFG0.LOOPBK` loops through the pad, not through the shifter

Three runs, each one ruling out something the previous could not:

| run | configuration | record | what it proved |
|---|---|---|---|
| 1 | loopback on, no pads routed | `matched=0 seen=0 cfg0=0x00000002 st=0x00003063` | the bit is set, both enables are on (`RXENS\|TXENS`), and the receiver still stays empty |
| 2 | loopback on, `SYNCBUSY` waits added to the enable path | identical | the missing sync was not the cause (worth adding anyway — see below) |
| 3 | loopback on, **TX/RX routed to two pads, nothing wired to them** | `matched=8 seen=8` | the loop closes through the receiver's input path |

So on this block `LOOPBK` connects the transmitter's output to the receiver's *input selection*, and an unrouted
receiver has no input to select. Nothing has to be wired to either pad; the pads only have to exist and be routed. The
`EUSART0` instrument never showed this because it routes its pads for its control run, and the loopback run inherits
them.

The two defects fixed on the way, both of the same class as the timer's:

- `CMD.TXEN`/`CMD.RXEN` are **commands**, not configuration: they cross into the block's own clock domain and
  `SYNCBUSY.TXEN`/`RXEN` say whether they landed. The driver raised `EN` without waiting. A bounded
  `wait_enables` now does, and the instrument records `STATUS` so a block that is enabled on paper but not in the
  protocol domain is visible as a number.
- `STATUS` and `CFG0` readbacks were not exposed, which made the first two runs indistinguishable from a driver that
  refused the request. `EusartN::status()` and `EusartN::cfg0()` now exist for exactly that reason, and
  `cfg0=0x00000002` is what makes "the loopback was on" a measurement rather than a claim.

## The record

Three flashes of the same image, three boots, `status=PASS` in all three, byte-identical:

```
eusart1: n=8 matched=8 seen=8 cfg0=0x00000002 st=0x00003063 control=0 div=297 want=115200 err=0x00000000 routed=1 refused=1
```

| field | meaning |
|---|---|
| `n=8 matched=8 seen=8` | eight distinct bytes — including `0x00` and `0xFF` — out and back, all eight identical; `seen` counts what the receiver handed over, so a mismatch would show as `matched < seen` |
| `cfg0=0x00000002` | `LOOPBK` as the block has it, not as the driver asked for it |
| `st=0x00003063` | `RXENS`, `TXENS`, `TXFL`, `RXFL` and two mode bits: the receiver and transmitter were both enabled |
| `control=0` | **control**: the same eight bytes written with the loopback off produced zero bytes at the receiver |
| `div=297` | the divider the driver computed for 115 200 at 16x oversampling |
| `err=0x00000000` | `RXOF`, `PERR`, `FERR` all clear |
| `routed=1` | **the finding**: the two pads were routed, without which the run above reads `matched=0 seen=0` |
| `refused=1` | **control**: a second `board.eusart1_async(...)` was refused by name |

## What this does not prove

- **A wire.** Nothing leaves the block, so this says nothing about a pad's level or a device at the other end. That is
  the "SPI/EUSART with a device on the pads" line in section 3 of the boundary, and it needs a witness this bench does
  not have.
- **The baud on a wire.** Both ends of a loopback share one divider, so a rate wrong by 20 % still passes here.
  `hal_eusart_loopback` times `EUSART0` against the SYSRTC for that reason; this instrument does not, because
  `EUSART1` has no clock selector to read back and a ratio against an assumed source would be an assumption wearing a
  number.
- **Interrupts.** Nothing here takes one.
